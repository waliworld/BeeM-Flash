# DME checksum schemes — research

What checksum each supported DME uses, and what is (and isn't) safe to rely on.
**Flashing a wrong checksum/region bricks the ECU — this records only what is
verified, and marks the rest clearly as to-be-confirmed.**

## Algorithm — confirmed

Every B58/S58 **BMW MG1CS** A2L in `mgflasher-map-packs` declares the checksum
method for its code/data flash segments as **`XCP_CRC_32`**:

```
/begin MEMORY_SEGMENT Pst80080000
  CODE FLASH INTERN 0x80080000 0x67F7E0 ...
  /begin IF_DATA XCPplus 0x0102
    /begin SEGMENT ... /begin CHECKSUM XCP_CRC_32 /end CHECKSUM ...
```

`XCP_CRC_32` is the **standard CRC-32** (IEEE 802.3: poly `0x04C11DB7`, reflected
`0xEDB88320`, init `0xFFFFFFFF`, refin/refout, xorout `0xFFFFFFFF`) — the same
CRC `checksum.js` implements as `crc32`. Confirmed for:

| DME | Engine | Covered segments (from the A2L; per-version) |
|-----|--------|----------------------------------------------|
| `MG1CS201` | B58/B48 Gen2 | code `0x80080000`+`0x67F7E0`, `0x80028000`+`0x37D00`; data `0x80700000`+`0xFF7E0` … |
| `MG1CS049` | S58 | same layout as MG1CS201 |
| `MG1CS003` | B58 Gen1 | code `0x09040000`+`0x63F7E0`, `0x09000000`+`0x3FD00`; data `0x09680000`+`0xFF7E0` … |

Per-DME templates with the exact ranges are generated by
`scripts/scheme_from_a2l.py` into `*.template.json` here.

## What is NOT settled (do not guess)

1. **Where the stored CRC lives.** The A2L gives the algorithm and the covered
   ranges, not the address the bootloader reads the stored CRC from. The
   templates leave `store.at` as a TODO — fill it from the bin / WinOLS, do not
   guess.
2. **The automotive block layout differs from motorcycle MG1.** The MIT
   `NetworkDir/moto-ecu-checksum` project documents a confirmed MG1 scheme
   (CRC-32 reflected, init `0xACC08E37`, big-endian CRC at the end of each
   `DE AD BE EF`…`12 34 56 78`-fill block). We ported it (`checksum.js`,
   `preset: 'bosch-mg1'`) **and tested it against the BMW stock bins — it finds
   none of those blocks**, so BMW MG1CS uses a different layout. `bosch-mg1` is
   for motorcycle MG1 (MG1CA094) / Bosch MSE8.0, not BMW.
3. **RSA signature.** Two independent sources state MG1/MD1 calibrations also
   carry a cryptographic **signature** that a correct CRC does not satisfy — the
   ECU only accepts a modified file the flash tool has patched. A CRC fix alone
   may not be enough on these DMEs.

## Binary analysis of the stock images (verified)

Using the stock bins directly (file offset = address − `0x80000000`, confirmed by
the EPK sitting at `ADDR_EPK`), the MG1CS201 (B58 Gen2) and MG1CS049 (S58) images
share this flash **tail** layout (`scripts/analyze_mg1_crc.py`,
`scripts/recover_mg1_crc.py`):

| file offset | contents |
|---|---|
| … `0x7FFCF8` | a `12 34 56 78` fill run, then a 4-byte checksum word (`8C7D85F2` on one image) |
| `0x7FFD00` – `0x7FFE00` | **256 bytes, entropy ≈ 7.1 bits/byte → a cryptographic signature (RSA/ECC)** |
| `0x7FFE00` + | identification block: the calibration ID (`00 00 5D 55 28 96 06` …), part/SW numbers, model strings |
| `0x7FFFDC` | a 4-byte header checksum word (`6D819588` on one image) |

The CRC words are real but do **not** reproduce under a standard CRC-32 over the
obvious ranges — the covered range and/or parameters are non-trivial and would
need the ECU's verification routine (TriCore disassembly) to pin down exactly.

## The real gate is the signature, not the checksum

The 256-byte high-entropy block is a **cryptographic signature** the ECU verifies.
**Correcting the CRC does not make the ECU accept a modified calibration** — this
matches the public reports that MG1/MD1 "only accept a file the flash tool has
patched." Satisfying it would require the manufacturer's private key (infeasible)
or a **bootloader signature-check bypass/exploit**.

**BeeM-Flash does not forge the signature or bypass the signature check**, and
this project will not build that. The checksum engine corrects CRCs — a
legitimate step — for a vehicle whose bootloader already accepts the write (e.g.
an owner's bench/boot-mode unlock). Making a signed-flash ECU accept an unsigned
modified calibration is a security-control bypass and is out of scope.

## How to complete a scheme safely

- Start from the DME's `*.template.json` (correct algorithm + ranges).
- Get the **store location** and confirm the **CRC init/seed + endianness** from
  the WinOLS **Bosch MDG1 (OLS830)** checksum plugin or your tuning tool, on your
  own stock bin, and verify the computed CRC matches the stored one on a known
  stock file **before** using it to flash.
- Supply it to BeeM-Flash as the descriptor `checksum` or `config.checksum`. The
  engine then checks on load and corrects (or refuses) before writing.
